# SwasthyaVaani - Project Architecture

This document outlines the high-level architecture, technology stack, and core
components of the **SwasthyaVaani** platform. It is designed to serve as a
reference for presentations and technical overviews.

> **Note on status labels used throughout this document:** Sections marked
> **[Implemented]** describe functionality present in the current prototype.
> Sections marked **[Designed / Proposed]** describe the solution design for
> capability being built out toward the full SIH build — this is the scope of
> what SwasthyaVaani is architected to deliver.

---

## 1. High-Level Overview

SwasthyaVaani is a comprehensive, AI-driven healthcare platform designed to
streamline patient intake, assist clinicians with automated clinical
summaries, and provide hospital administrators with operational insights. A
core pillar of the platform is dual-system clinical intelligence — capturing
both modern-medicine history and traditional AYUSH (Ayurveda, Yoga, Unani,
Siddha, Homeopathy) assessment within the same adaptive interview engine.

The application is structured as a modern decoupled **Client-Server
Architecture**:
* **Frontend (Client):** A responsive Single Page Application (SPA) built
  with React and Vite, catering to Patients, Doctors, and Administrators.
* **Backend (Server):** A high-performance RESTful API powered by FastAPI
  (Python), integrating with various AI/ML services for intelligent intake
  and document processing.
* **Database:** Relational database for structured data storage (SQLite for
  local dev, PostgreSQL/Supabase ready for production).

## 2. Technology Stack

### Frontend (User Interface)
* **Core Framework:** React 19 + TypeScript
* **Build Tool:** Vite (for fast HMR and optimized builds)
* **Routing:** Wouter (lightweight router)
* **Styling & UI:**
  * Tailwind CSS v4 (Utility-first styling)
  * Radix UI (Accessible, unstyled primitives)
  * shadcn/ui (Component system built on Radix + Tailwind)
  * Framer Motion (for fluid animations and transitions)
* **State & Data Fetching:** React Query (`@tanstack/react-query`)
* **Forms:** React Hook Form + Zod (Validation)
* **Data Visualization:** Recharts

### Backend (API & Business Logic)
* **Framework:** FastAPI (Python 3) — chosen for its async capabilities and
  automatic OpenAPI documentation.
* **Server:** Uvicorn (ASGI server)
* **ORM:** SQLAlchemy 2.0
* **Database Migrations:** Alembic
* **Database:** SQLite (`swasthyavaani.db` local) with dependencies present
  for PostgreSQL (Supabase / psycopg2).
* **Authentication:** PyJWT (JSON Web Tokens)

### AI, ML & Integrations
* **LLM Providers:** Google GenAI, Groq (used for conversational intake,
  generating dynamic questions, and clinical summarization).
* **Document Intelligence:** PaddleOCR and PaddlePaddle (for extracting text
  from uploaded medical documents/prescriptions).
* **RAG (Retrieval-Augmented Generation):** Custom RAG pipelines for
  contextual clinical insights, including AYUSH-specific reference data
  **[Designed / Proposed]**.
* **Speech-to-Text / TTS:** Voice intake capabilities via Sarvam ASR and
  Bulbul TTS (`speech.py`).
* **Healthcare Standards:** Integrations built for ABDM (Ayushman Bharat
  Digital Mission) and FHIR (Fast Healthcare Interoperability Resources).

## 3. Core Modules & Workflows

### A. Patient Portal (`/patient/*`)
Provides a multilingual, voice-first intelligent intake experience.
* **Features:** Language selection, demographic details, conversational
  symptom checker, AYUSH assessment branch, and profile management.
* **Mechanism:** Driven by the `IntakeSession` backend model, the system asks
  dynamic questions based on patient responses, capturing data as
  `QuestionEvent` and `Answer` models. When the workflow type is AYUSH or
  dual-system, the adaptive engine routes into the AYUSH Assessment Engine
  described in Section 6.

### B. Doctor/Clinician Portal (`/doctor/*`)
An AI-assisted dashboard for physicians to review patient cases before the
actual consultation.
* **Features:** Patient queue, detailed AI summaries, extracted red flags,
  consultation transcript (chat/voice), SOCRATES-structured symptom cards,
  and AYUSH-specific visualizations (Prakriti/Vikriti distribution, Agni and
  Koshtha indicators, Dashavidha Pariksha summary panel — see Section 6).
* **Mechanism:** Consumes `ClinicalStateModel`, `AyushAssessmentModel`, and
  `RedFlagModel` generated by the backend AI to present a concise clinical
  picture across both modern-medicine and AYUSH systems.

### C. Admin & Hospital Operations (`/admin/*`)
Tools for hospital staff to manage facilities and oversee operations.
* **Features:** Hospital onboarding, AI monitoring, emergency management,
  audits, and QA dashboards.

## 4. Database Schema Overview

The relational database is structured to handle healthcare entities
robustly. Key tables include:

* **Users & Roles:** `users`, `patients`, `doctors`, `hospitals`,
  `departments`.
* **Clinical Intake:**
  * `intake_sessions`: Tracks the entire conversational flow of a patient.
  * `question_events` & `answers`: The turn-by-turn dialogue history.
* **AI Insights:**
  * `clinical_states`: The evolving structured clinical summary generated by
    the LLM.
  * `ayush_assessments`: The structured Dashavidha Pariksha and Ahara-Vihara
    record for a session **[Designed / Proposed — see Section 6.3]**.
  * `red_flags`: Critical symptoms or contradictions flagged for immediate
    doctor attention.
  * `physician_reviews`: Final assessments made by the doctor.

## 5. Detailed Data Flows & Processes

### A. Intelligent Patient Intake Flow
1. **Initiation (`POST /api/v1/intakes`)**:
   - Patient starts a session, selecting workflow type (`GENERAL_CLINICAL`,
     `AYUSH`, or `DUAL_SYSTEM`).
   - An `IntakeSession` and an initial empty `ClinicalStateModel` are
     created; if AYUSH-relevant, an empty `AyushAssessmentModel` is attached.
2. **Interaction & AI Thinking Engine
   (`POST /api/v1/intakes/{id}/voice-answer` or `/answers`)**:
   - **Voice/Text Ingestion**: Audio is transcribed via Sarvam ASR
     (Speech-to-Text).
   - **Fact Extraction**: The natural language answer is passed to the LLM
     (Google GenAI/Groq). The LLM extracts clinical facts (symptoms,
     duration, severity) and, where relevant, AYUSH-specific facts (dietary
     pattern, sleep/digestion quality, physical build, activity tolerance).
   - **State Mutation**: Extracted facts are merged into the versioned
     `ClinicalStateModel` and, in parallel, into the `AyushAssessmentModel`.
   - **Adaptive Questioning**: The `evaluate_next_question` engine analyzes
     the updated clinical state — spanning both modern and AYUSH fields — and
     decides whether to `ASK` another question (from either question bank),
     `STOP` if sufficient data is gathered, or `RED_FLAG_ESCALATE`.
   - **TTS Synthesis**: If a new question is formulated, Sarvam Bulbul TTS
     converts it to speech for the patient.
3. **Submission & Triage (`POST /api/v1/intakes/{id}/submit`)**:
   - The session is marked as `SUBMITTED`.
   - The system evaluates the final clinical state for `RedFlagModel`
     entries (critical symptoms).
   - A priority badge (e.g., URGENT vs. NORMAL) is assigned.
   - A WebSocket event (`NEW_PATIENT_INTAKE`) is broadcast to the doctor's
     live queue, carrying both the clinical and AYUSH summary payloads.

### B. Doctor Review & Confirmation Flow
1. **Live Queue (`GET /api/v1/doctor/queue`)**:
   - The doctor's dashboard subscribes to WebSocket updates.
   - The queue API batch-fetches pending patients, ordering them by triage
     priority and wait time.
2. **Clinical Review (`GET /api/v1/doctor/patients/{id}`)**:
   - The doctor selects a patient and views the structured `ClinicalState`,
     including chief complaints, extracted medical history, AI-flagged red
     flags, and — for AYUSH/dual-system cases — the full Dashavidha Pariksha
     panel and Ahara-Vihara summary.
   - The doctor can also view the raw conversational timeline (Questions &
     Answers).
3. **Physician Confirmation (`POST /api/v1/doctor/patients/{id}/confirm`)**:
   - The doctor makes any necessary manual edits to the AI's summary,
     including AYUSH parameter corrections.
   - The system generates a `PhysicianReviewModel` and records
     `AuditEventModel` logs.
   - Optionally, the backend generates an interoperable **FHIR R4 Bundle**
     for seamless sharing with other hospital systems.

### C. Document Intelligence Flow (Medical Records)
1. **Secure Upload (`POST /api/v1/documents/upload`)**:
   - The patient uploads a medical document (e.g., prescription, past
     reports, prior Ayurvedic case sheet).
   - The document is validated, hashed (SHA-256) for deduplication, and
     securely stored. A `DocumentModel` is created.
2. **OCR Processing (`POST /api/v1/documents/{id}/process`)**:
   - The document is sent to PaddleOCR.
   - Text, bounding boxes, and confidence scores are extracted.
   - The system maps raw text to structured `ExtractedFact` objects (e.g.,
     medications, dosages, lab values) and stores them in
     `DocumentExtractionModel` for human review. Extracted lab values are
     checked against reference ranges and flagged if abnormal
     **[Designed / Proposed]**; extracted medications are checked against a
     drug-interaction reference set **[Designed / Proposed]**.

## 6. AYUSH Assessment Engine — Solution Design

This is SwasthyaVaani's primary differentiator against generic intake or
triage tools, and the module most directly aligned with the AYUSH-specific
requirements of the problem statement. It is designed as a parallel
assessment track inside the same adaptive interview engine used for modern
medicine — not a bolted-on separate form.

### 6.1 Design Principle: Dual-System, Single Engine

Rather than treating AYUSH intake as a separate app or a static
questionnaire, the adaptive engine treats Dashavidha Pariksha parameters as
information-gap targets exactly like SOCRATES fields (onset, duration,
severity, etc.) for modern medicine. This means:

* One conversational flow, not two disconnected forms.
* The same duplicate-detection, information-gain scoring, and
  `MAX_QUESTIONS` safety ceiling apply to AYUSH questions as to clinical
  questions — no separate, unbounded questionnaire.
* A workflow selector (`GENERAL_CLINICAL` / `AYUSH` / `DUAL_SYSTEM`) decides
  whether AYUSH targets are included in the gap-analysis pass for a given
  session, so a general OPD patient isn't asked irrelevant questions.

### 6.2 Dashavidha Pariksha — Full Parameter Coverage

The AYUSH Assessment Engine is designed to capture all ten classical
examination parameters, plus Ahara-Vihara, as first-class fields:

| Parameter | What It Captures | Example Adaptive Question |
|---|---|---|
| **Prakriti** | Constitutional body-mind type (Vata/Pitta/Kapha dominance) | "Would you describe your build as naturally thin and light, medium and warm, or solid and steady?" |
| **Vikriti** | Current state of dosha imbalance vs. baseline constitution | "Compared to how you normally feel, what's changed recently?" |
| **Sara** | Tissue (dhatu) quality and essence | Inferred from skin, hair, and general vitality descriptors gathered during intake |
| **Samhanana** | Body compactness / structural build | Captured via build and frame descriptors |
| **Pramana** | Physical measurements and proportion | Height/build context captured during demographic + physical questions |
| **Satmya** | Habituation — what agrees with the patient (climate, food, season) | "Are there foods or seasons that tend to suit you particularly well or badly?" |
| **Sattva** | Mental/psychological strength and resilience | "How would you describe your ability to handle stress or discomfort?" |
| **Ahara Shakti** | Digestive capacity and appetite pattern | "How would you describe your appetite and digestion generally?" |
| **Vyayama Shakti** | Exercise/exertion tolerance | "How much physical activity can you comfortably do before feeling tired?" |
| **Vaya** | Age-related constitutional stage | Derived from patient age at intake |

Alongside this, **Ahara-Vihara** (diet and lifestyle) is captured as a
structured sub-record: meal pattern, sleep pattern, activity level, and
notable lifestyle factors — feeding directly into the Agni (digestive
capacity) and Koshtha (bowel nature) fields already present in the current
`ClinicalState.ayush` object.

### 6.3 Data Model — `AyushAssessmentModel` (Proposed Extension)

```python
class AyushAssessmentModel(BaseModel):
    session_id: str
    prakriti: Optional[DoshaProfile] = None          # Vata/Pitta/Kapha distribution
    vikriti: Optional[DoshaProfile] = None
    sara: Optional[str] = None
    samhanana: Optional[str] = None
    pramana: Optional[str] = None
    satmya: Optional[str] = None
    sattva: Optional[str] = None
    ahara_shakti: Optional[str] = None                # digestive capacity
    vyayama_shakti: Optional[str] = None              # exertion tolerance
    vaya: Optional[str] = None                        # constitutional life-stage
    agni: Optional[str] = None                        # existing field, retained
    koshtha: Optional[str] = None                     # existing field, retained
    ahara_vihara: Optional[AharaViharaProfile] = None # diet/lifestyle sub-record
    confidence_scores: Dict[str, float] = {}
    source: Literal["PATIENT_STATED", "AI_INFERRED", "PHYSICIAN_CONFIRMED"]
```

This extends (not replaces) the existing `AyushState` object referenced in
`ClinicalState`, so the current Prakriti/Agni/Koshtha fields remain
backward-compatible while the model grows to cover all ten parameters.

### 6.4 Doctor-Facing AYUSH Visualization

On the Doctor Portal, the AYUSH panel is designed to present:

* A **Dosha distribution gauge** (Vata/Pitta/Kapha proportions) for both
  Prakriti (baseline) and Vikriti (current imbalance), so the physician can
  see deviation from constitution at a glance.
* A **Dashavidha Pariksha summary card** listing all ten parameters with
  patient-stated values, each tagged by source (patient-stated / AI-inferred
  / physician-confirmed) — consistent with the platform's existing
  provenance-tracking principle used for modern-medicine facts.
* An **Ahara-Vihara snapshot** (diet, sleep, activity) alongside the Agni/
  Koshtha indicators already implemented.

### 6.5 Safety Boundary (Consistent with Platform-Wide Rule)

As with all AI-assisted output on SwasthyaVaani, the AYUSH Assessment Engine
**never outputs an autonomous Ayurvedic diagnosis or treatment
recommendation**. Its output is a structured, physician-reviewable
constitutional and lifestyle profile — the AYUSH-qualified physician remains
the sole clinical decision-maker, exactly as for the modern-medicine track.

## 7. Roadmap Note

Fields and flows marked **[Designed / Proposed]** throughout this document
represent the target solution architecture for the full build. The current
prototype implements the core adaptive engine, modern-medicine SOCRATES
flow, baseline AYUSH fields (Prakriti, Vikriti, Agni, Koshtha), document OCR,
and the doctor/admin portals described in Sections 3–5. The AYUSH Assessment
Engine expansion (Section 6) and document-level abnormal-value/drug-
interaction flagging represent the next build phase.
